## Findings addressed

### Generation and saved business data

- **DeepSeek request handling:** the three shipped generators now share `deepseek-flash` model selection and explicit non-thinking mode. The shared `deepseek_response.py` rejects missing, empty, truncated, filtered, and otherwise interrupted completions before parsing or saving them. A cutoff does not cause an additional composition-repair request.
- **Copy-preserving redesign:** requesting Redesign without saved approved copy now stops before a model request, with an instruction to use Rebuild when new copy is wanted.
- **Failed rebuild recovery:** the dashboard/batch pipeline backs up an existing website and approved copy before replacement. Rendering, file-write, or validation failures restore those files while retaining a failed job status and invalidating delivery approval. A restoration failure retains the backup and reports its location. Standalone legacy generator invocations do not run through this pipeline protection.
- **Repeated searches:** newly discovered fields update the existing business record while preserving saved services, SEO settings, design references, and other enrichment. Exact business-name/address matches whose priority changes move with their saved website and copy; another business with the same name is protected from replacement. Existing duplicate records are not automatically merged.
- **Validation and batch recovery:** escaped verified business names are recognized in rendered text, and names containing words such as “Certified” do not become invented claims by themselves. Malformed status files and incomplete websites no longer count as completed work during batch resume. Runs started in the same second receive separate log folders.
- **Concurrent usage logging:** updates are serialized and saved through atomic replacement. Logging failure does not turn a valid composition response into a failed generation.

Evidence: `tests/test_core_audit.py`, `tests/test_audit_regressions.py`, `tests/test_leadfinder_fixes.py`, and the existing reference, craft, color, and composition suites.

### Dashboard, previews, and exports

- **Independent CSV downloads:** each export owns its bytes instead of sharing a file that another request can replace. Exports preserve Unicode, keep web-sourced formula-like text as text, and do not overwrite existing saved CSV files.
- **Preview isolation:** the embedded preview and directly opened generated pages receive a sandbox boundary. Generated scripts can run within the preview but do not receive the dashboard's origin. Cross-origin font access is limited to font assets; workspace/API-settings endpoints do not receive a permissive CORS header.
- **Local request boundaries:** workspace routes reject nonlocal hostnames and mutations reject mismatched origins. Invalid search fields and invalid, redirected, or looping saved-business paths fail without starting provider work or breaking the complete business list.
- **Search/build coordination:** a search and website builds cannot modify the same handoff workspace concurrently. Builds for different businesses remain supported. Deletion retains its active-job checks and preserves removed files in `outputs/deleted_leads`.
- **Dashboard state recovery:** pending searches disable conflicting actions; a lost submission reply can reconnect to an already accepted job. Late search/build polling responses cannot replace a newer job. API-key saves lock their dialog while pending and ignore older test responses. Preview loading works without inspecting the sandboxed frame's document.

Evidence: `tests/test_dashboard_audit.py`, `tests/test_lead_deletion.py`, and `tests/test_dashboard.py`. Server contracts passed locally and in CI. All 22 dashboard browser tests passed in CI, including real-server preview isolation, loaded fonts/scripts, direct-tab isolation, mobile sizing, sorting/deletion, settings saves, and job recovery.

### Windows and distribution

- **Active-work protection during download repair:** the standalone downloader now delegates to the staged installer before replacing installed files. The installer's active-search/build check therefore runs before any installed source is overwritten.
- **Failed-start cleanup:** the launcher records its newly created process immediately. Startup failure or timeout attempts to stop only that process tree, checking the original process object, executable, entrypoint, and creation time. Existing reused workspaces and unrelated applications are excluded. The normal readiness deadline remains 60 seconds.
- **Complete ZIP replacement:** the package builder validates all selected files, including the installer, configuration template, and required dashboard CSS, before writing. Linked files and inputs resolving outside the source root are rejected. The previous ZIP remains intact if a later read/write fails; a temporary archive replaces it only on success.
- **Installer layouts and preservation:** repository setup remains in that checkout; an extracted ZIP installs to the normal local application folder. Existing keys, saved businesses, and outputs are preserved. Windows regressions cover both wrapper layouts, error codes, paths containing spaces/apostrophes/ampersands/parentheses, active-work update refusal, and cleanup of a nonresponsive startup.

Evidence: `tests/test_windows_distribution.py` and `tests/test_windows_launcher.py`. The six distribution tests passed locally. The new packaging regressions were also run against the old builder and reproduced the missing-input, linked-input, and interrupted-write failures. All 12 Windows regression tests subsequently passed in CI, including startup-timeout process cleanup while preserving an unrelated Python process.
